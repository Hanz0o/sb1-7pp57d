Next.js Architecture

Two layouts (landing & store) via ROUTE GROUPS; dynamic routes for collections & products. 

app/
├── (landing)/                # Route group · BARE layout (NO navbar/footer) → immersive brand
│   ├── layout.tsx            #   renders only {children} + <BrandLoader/>
│   └── page.tsx              #   Section 2 · fullscreen 100vh hero, two CTAs
│
├── (store)/                  # Route group · STORE layout (Navbar + Footer + Cart)
│   ├── layout.tsx            #   <Navbar/> {children} <Footer/>  ← the "chrome appears" mechanism
│   │
│   ├── collections/          # Section 3 & 4 · Collection Hub + dynamic collections
│   │   ├── page.tsx          #   the Hub — lists all collections from CMS
│   │   └── [slug]/           #   Section 5 · DYNAMIC route → pre-filtered shop
│   │       └── page.tsx      #   getProducts({ collectionSlug: slug, ...searchParams })
│   │
│   ├── filmora/              # Section 6 · BESPOKE editorial page (its own custom layout)
│   │   └── page.tsx          #   NOT the [slug] template — hand-built art direction
│   │
│   ├── products/             # Product detail
│   │   └── [handle]/         #   DYNAMIC route by product handle
│   │       └── page.tsx      #   gallery + variants + live stock + add-to-cart
│   │
│   ├── cart/                 # Step 7 · cart review (page or slide-over drawer)
│   │   └── page.tsx
│   │
│   └── checkout/             # Step 8 · checkout (server actions + payment intent)
│       └── page.tsx
│
├── api/ (or /lib server)     # getCollections(), getProducts(), createOrder() → CMS + Inventory
└── globals.css               # brand tokens (this file's <style> + tailwind theme)

(landing) — a route group (parentheses = no URL segment). Its layout has NO chrome, producing the immersive brand threshold. This is WHY the navbar/footer are absent on the first screen.

(store) — the second layout. Its layout.tsx wraps children in Navbar + Footer, so every page under it automatically gains the shopping chrome. Crossing from (landing) to (store) swaps layouts = "the store appears".

collections/ — the Hub (Section 3) plus [slug] dynamic pages (Sections 4–5). New CMS collections become new URLs with zero code.

filmora/ — deliberately separate from [slug] so the flagship keeps its bespoke editorial layout (Section 6).

products/[handle]/ — product detail; specs + stock from Inventory, story from CMS.

checkout/ — final conversion; server actions decrement stock and create the order.

Inventory & Data Model

The Admin Panel controls everything; the storefront only reads. Relationships below.

InventoryItem

  • id · name · handle · sku
  • price · currency (AED)
  • metal · stone · carat
  • stockQuantity
  • isFeatured (flag)
  • isPublished

Collection

  • id · name · slug
  • coverImage · description
  • sortOrder
  • type: featured | campaign | occasion
  • publishWindow (start/end)

collection_products

  • collection_id (FK)
  • product_id (FK)
  • position (sort within collection)
  • ↳ MANY-TO-MANY join table

One InventoryItem can belong to many Collections (Featured + Eid + Wedding simultaneously).

Campaign & Occasion are just Collections with a type — same table, different behavior/scheduling.

Featured = a boolean flag for quick spotlights, or the 'featured' collection for a curated edit.

Storefront queries: getProducts({'{'} collectionSlug, inStockOnly: true {'}'}) → always live, never hardcoded.
